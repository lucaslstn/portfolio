1. Architecture Globale

                          ┌──────────────────────────────────┐
           Internet ──▶   │   VIP : 10.0.0.82 (Keepalived)   │
                          └──────────────┬───────────────────┘
                                         │ VRRP failover automatique
          ┌──────────────────────────────┴──────────────────────────────┐
          │                                                              │
┌─────────▼─────────────────────┐              ┌───────────────────────▼──────────────────┐
│  HAProxy Node 1 (MASTER)      │              │  HAProxy Node 2 (BACKUP)                 │
│  10.0.0.80                    │◀── VRRP ────▶│  10.0.0.81                               │
│  · Routing HTTP/HTTPS         │              │  · Routing HTTP/HTTPS                    │
│  · Passerelle Internet        │              │  · Passerelle Internet                   │
│    des backends (NAT)         │              │    des backends (NAT)                    │
└─────────┬─────────────────────┘              └──────────────────────────────────────────┘
          │
          │  ← trafic Internet entrant (routing ACL par domaine / path)
          │  → trafic sortant des backends vers Internet (NAT)
          │
 ┌────────┴────────┐
 │                 │
 ▼                 ▼
┌──────────────┐  ┌──────────────┐
│  Backend 1   │  │  Backend 2   │
│  10.1.0.80   │  │  10.1.0.81   │
│              │  │              │
│  ✗ pas       │  │  ✗ pas       │
│  d'accès    │  │  d'accès    │
│  Internet    │  │  Internet    │
│  direct      │  │  direct      │
└──────────────┘  └──────────────┘

Principe de fonctionnement :

  • Keepalived gère une IP Virtuelle (VIP 10.0.0.82) entre les deux nœuds via le protocole VRRP. Le nœud MASTER détient la VIP. Si le MASTER disparaît (crash, réseau), le BACKUP prend la VIP en moins de 2 secondes.
  • HAProxy tourne sur les deux nœuds et reçoit le trafic entrant via la VIP. Il inspecte les requêtes HTTP/HTTPS et les route vers les backends via des ACLs (par nom de domaine ou par path).
  • Passerelle Internet des backends : les serveurs backends (10.1.0.80, 10.1.0.81) n’ont aucune interface exposée directement sur Internet. Tout leur trafic sortant (mises à jour système, appels API externes, etc.) transite obligatoirement par le nœud HAProxy actif qui assure le NAT. Cela réduit la surface d’attaque : un attaquant ne peut pas joindre un backend directement depuis l’extérieur.
  • HAProxy surveille la santé des backends en continu via des health-checks HTTP.

2. Prérequis Système

2.1 Paquets à installer

apt update && apt install -y \
    haproxy \         # Load balancer
    keepalived \      # Gestion de la VIP VRRP
    certbot           # Génération des certificats SSL Let's Encrypt

2.2 Paramètres Kernel

HAProxy doit pouvoir se bind sur la VIP (10.0.0.82), même si celle-ci n’est pas encore assignée localement (cas du nœud BACKUP). Sans ce paramètre, HAProxy ne démarre pas sur le BACKUP.

# Activation à chaud (non persistant, pour test)
sysctl -w net.ipv4.ip_nonlocal_bind=1

# Activation persistante (survit aux reboots)
echo "net.ipv4.ip_nonlocal_bind = 1" >> /etc/sysctl.d/99-haproxy.conf
sysctl -p /etc/sysctl.d/99-haproxy.conf

Vérification :

sysctl net.ipv4.ip_nonlocal_bind
# Attendu : net.ipv4.ip_nonlocal_bind = 1

2.3 Pare-feu (si actif)

# Autoriser le protocole VRRP entre les deux nœuds (multicast 224.0.0.18)
iptables -A INPUT  -p vrrp -j ACCEPT
iptables -A OUTPUT -p vrrp -j ACCEPT

# Autoriser le trafic HTTP/HTTPS entrant sur la VIP
iptables -A INPUT -p tcp --dport 80  -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# Autoriser l'interface de stats HAProxy (port 8404, accès restreint)
iptables -A INPUT -p tcp --dport 8404 -s 10.0.0.0/24 -j ACCEPT

3. Configuration Keepalived

Le fichier de configuration est identique sur les deux nœuds à l’exception de state et priority.

3.1 HAProxy Node 1 — MASTER (10.0.0.80)

# /etc/keepalived/keepalived.conf — HAProxy Node 1 (MASTER)
# Script de health-check : Keepalived vérifie que HAProxy est vivant.
# Si HAProxy crashe sur le MASTER, la VIP bascule sur le BACKUP.
vrrp_script chk_haproxy {
    script "/usr/bin/killall -0 haproxy"  # Retourne 0 si le process existe
    interval 2                             # Vérification toutes les 2 secondes
    weight   -20                           # Réduit la priorité de 20 si le check échoue
}

vrrp_instance VI_1 {
    state  MASTER                 # Ce nœud est le MASTER au démarrage
    interface eth0                # Interface réseau qui porte la VIP (adapter si nécessaire : ens3, bond0...)
    virtual_router_id 51          # Identifiant VRRP unique pour ce groupe (doit être identique sur les deux nœuds)
    priority  101                 # Priorité plus haute que le BACKUP (100) → gagne l'élection au démarrage
    advert_int 1                  # Envoi d'un heartbeat VRRP toutes les 1 seconde

    authentication {
        auth_type PASS
        auth_pass S3cur3VRRPp4ss   # Mot de passe VRRP partagé (CHANGER EN PROD)
    }

    virtual_ipaddress {
        10.0.0.82/24              # La VIP que ce groupe gère
    }

    track_script {
        chk_haproxy               # Lie le résultat du health-check à la priorité de ce nœud
    }
}

3.2 HAProxy Node 2 — BACKUP (10.0.0.81)

# /etc/keepalived/keepalived.conf — HAProxy Node 2 (BACKUP)
vrrp_script chk_haproxy {
    script "/usr/bin/killall -0 haproxy"
    interval 2
    weight   -20
}

vrrp_instance VI_1 {
    state  BACKUP                 # Ce nœud démarre en mode BACKUP
    interface eth0
    virtual_router_id 51          # Doit être identique au MASTER
    priority  100                 # Priorité inférieure au MASTER (101)
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass S3cur3VRRPp4ss  # Doit être identique au MASTER
    }

    virtual_ipaddress {
        10.0.0.82/24
    }

    track_script {
        chk_haproxy
    }
}

3.3 Activation

systemctl enable --now keepalived

# Vérifier que la VIP est bien assignée sur le MASTER
ip addr show eth0 | grep 10.0.0.82

4. Configuration HAProxy

4.1 Structure du fichier

# /etc/haproxy/haproxy.cfg

4.2 Section global

global
    log /dev/log local0               # Envoi des logs vers syslog
    log /dev/log local1 notice
    chroot      /var/lib/haproxy      # Jail filesystem pour réduire la surface d'attaque
    stats socket /run/haproxy/admin.sock mode 660 level admin expose-fd listeners
    stats timeout 30s

    user  haproxy                     # Déescalade de privilèges après bind
    group haproxy

    daemon                            # Lance HAProxy en background

    # --- Hardening SSL/TLS ---
    ssl-default-bind-ciphers   ECDH+AESGCM:DH+AESGCM:ECDH+AES256:DH+AES256:ECDH+AES128:DH+AES:RSA+AESGCM:RSA+AES:!aNULL:!MD5:!DSS
    ssl-default-bind-options   no-sslv3 no-tlsv10 no-tlsv11   # Désactive les protocoles obsolètes
    ssl-default-server-ciphers ECDH+AESGCM:DH+AESGCM:ECDH+AES256:DH+AES256:ECDH+AES128:DH+AES:RSA+AESGCM:RSA+AES:!aNULL:!MD5:!DSS
    ssl-default-server-options no-sslv3 no-tlsv10 no-tlsv11

    tune.ssl.default-dh-param 2048    # Taille minimale des paramètres DH pour le forward secrecy

4.3 Section defaults

defaults
    log     global
    mode    http                      # Mode HTTP (inspection L7, nécessaire pour les ACLs)
    option  httplog                   # Log des requêtes HTTP (méthode, URL, code réponse)
    option  dontlognull               # Ignore les health-checks qui ne génèrent pas de requête HTTP

    timeout connect  5s               # Délai max pour établir la connexion vers un backend
    timeout client   50s              # Délai max d'inactivité côté client
    timeout server   50s              # Délai max d'inactivité côté serveur

    errorfile 400 /etc/haproxy/errors/400.http
    errorfile 403 /etc/haproxy/errors/403.http
    errorfile 500 /etc/haproxy/errors/500.http
    errorfile 502 /etc/haproxy/errors/502.http
    errorfile 503 /etc/haproxy/errors/503.http

4.4 Interface de Statistiques

# --- Page de statistiques HAProxy ---
# Accessible sur http://10.0.0.82:8404/stats
# RESTREINDRE l'accès en production (ACL réseau ou authentification)
frontend stats
    bind *:8404
    stats enable                          # Active l'interface web de stats
    stats uri /stats                      # URL d'accès à la page de stats
    stats realm "HAProxy Statistics"      # Titre de la boîte d'authentification HTTP Basic
    stats auth admin:ChangeM3!            # Authentification HTTP Basic (CHANGER EN PROD)
    stats refresh 10s                     # Rafraîchissement automatique toutes les 10 secondes
    stats show-legends                    # Affiche la légende des colonnes
    stats show-node                       # Affiche le nom du nœud HAProxy actif
    no log                                # Ne pas polluer les logs avec les hits sur /stats

4.5 Frontend HTTP → Redirection HTTPS

# --- Frontend HTTP (port 80) ---
# Seul rôle : rediriger tout le trafic en HTTPS.
# Aucun routing applicatif ici, on ne touche pas au contenu.
frontend http_redirect
    bind 10.0.0.82:80                     # Écoute uniquement sur la VIP

    # Redirection permanente (301) vers HTTPS
    # Préserve le host et l'URI d'origine
    http-request redirect scheme https code 301

4.6 Frontend HTTPS — Routing par ACL

# --- Frontend HTTPS (port 443) ---
# Point d'entrée principal. Termine le TLS et route vers les backends via ACLs.
frontend https_frontend
    bind 10.0.0.82:443 ssl crt /etc/haproxy/certs/  # Dossier contenant les fichiers .pem (un par domaine)
    
    # Ajoute l'en-tête HSTS : force le navigateur à utiliser HTTPS pendant 1 an
    http-response set-header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"

    # Supprime les en-têtes qui divulguent des infos sur la stack serveur
    http-response del-header X-Powered-By
    http-response del-header Server

    # --- Définition des ACLs ---

    # ACLs par nom de domaine (SNI / Host header)
    acl host_site1  hdr(host) -i site1.148.sio
    acl host_site2  hdr(host) -i site2.148.sio

    # ACLs par path (URL) — utile si plusieurs apps partagent le même domaine
    acl path_site1  path_beg /site1
    acl path_site2  path_beg /site2

    # --- Règles de routing ---
    # Priorité : domaine d'abord, puis path en fallback

    # Routing par domaine (recommandé, plus propre)
    use_backend backend_site1  if host_site1
    use_backend backend_site2  if host_site2

    # Routing par path (activer si les deux sites partagent un domaine commun)
    # use_backend backend_site1  if path_site1
    # use_backend backend_site2  if path_site2

    # Backend par défaut si aucune ACL ne matche
    default_backend backend_site1

4.7 Backends

# --- Backend site1.148.sio ---
backend backend_site1
    balance roundrobin                          # Distribution en round-robin entre les serveurs

    # Health-check HTTP : HAProxy envoie une requête GET /health toutes les 5s.
    # Un serveur est marqué DOWN après 3 échecs, UP après 2 succès consécutifs.
    option httpchk GET /health
    http-check expect status 200

    # Réécriture du path : supprime le préfixe /site1 avant de transmettre au backend.
    # Sans cette ligne, le backend recevrait /site1/ma-page au lieu de /ma-page.
    http-request replace-path ^/site1(/.*)? \1

    # Ajout de l'IP réelle du client dans l'en-tête X-Forwarded-For
    option forwardfor

    server backend1 10.1.0.80:80 check inter 5s fall 3 rise 2  # inter : intervalle du health-check
    server backend2 10.1.0.81:80 check inter 5s fall 3 rise 2  # fall/rise : seuils DOWN/UP

# --- Backend site2.148.sio ---
backend backend_site2
    balance roundrobin

    option httpchk GET /health
    http-check expect status 200

    # Même logique de réécriture pour /site2
    http-request replace-path ^/site2(/.*)? \1

    option forwardfor

    server backend1 10.1.0.80:8080 check inter 5s fall 3 rise 2  # Site2 tourne sur le port 8080
    server backend2 10.1.0.81:8080 check inter 5s fall 3 rise 2

5. Gestion SSL — Certificats Auto-Signés (Local)

Comprendre le problème : pourquoi HAProxy est différent

Un certificat SSL est composé de deux fichiers distincts :

Fichier Contenu
cert.pem Le certificat (clé publique + infos du domaine)
key.pem La clé privée associée

HAProxy n’accepte pas deux fichiers séparés. Il exige un seul fichier .pem qui contient les deux, dans cet ordre : certificat d’abord, clé privée ensuite.

Certificat auto-signé vs certificat Let’s Encrypt : un certificat auto-signé est généré localement, sans passer par une autorité de certification externe. Il fonctionne parfaitement pour un réseau interne ou un environnement de lab (comme ici), mais le navigateur affichera un avertissement de sécurité car il ne reconnaît pas l’émetteur. C’est un comportement normal — il suffit d’accepter l’exception dans le navigateur.

Étape 1 — Installer openssl

apt install -y openssl

Étape 2 — Créer le dossier de certificats HAProxy

# Créer le dossier qui contiendra les certificats
mkdir -p /etc/haproxy/certs

# Restreindre l'accès : ce dossier contient des clés privées
chmod 700 /etc/haproxy/certs

Étape 3 — Générer le certificat auto-signé pour chaque domaine

La commande openssl req -x509 génère en une seule fois la clé privée ET le certificat auto-signé.

Pour site1.148.sio :

openssl req -x509 -newkey rsa:2048 -nodes -days 3650     -keyout /etc/haproxy/certs/site1.key.pem     -out    /etc/haproxy/certs/site1.cert.pem     -subj   "/C=FR/ST=Occitanie/L=Toulouse/O=BTS-SIO/CN=site1.148.sio"

Pour site2.148.sio :

openssl req -x509 -newkey rsa:2048 -nodes -days 3650     -keyout /etc/haproxy/certs/site2.key.pem     -out    /etc/haproxy/certs/site2.cert.pem     -subj   "/C=FR/ST=Occitanie/L=Toulouse/O=BTS-SIO/CN=site2.148.sio"

Explication des options :

Option Rôle
-x509 Génère un certificat auto-signé (pas une demande de signature CSR)
-newkey rsa:2048 Crée une nouvelle clé privée RSA de 2048 bits en même temps
-nodes Ne chiffre pas la clé privée (pas de mot de passe → HAProxy peut la lire sans intervention humaine)
-days 3650 Le certificat est valide 10 ans
-subj Renseigne les informations du certificat sans passer par un formulaire interactif
CN= Common Name : doit correspondre exactement au nom de domaine utilisé dans le navigateur

Étape 4 — Fusionner en un seul fichier .pem pour HAProxy

La commande cat colle les deux fichiers bout à bout.
L’ordre est impératif : certificat TOUJOURS en premier, clé privée en second.

# Fusion pour site1.148.sio
cat /etc/haproxy/certs/site1.cert.pem     /etc/haproxy/certs/site1.key.pem     > /etc/haproxy/certs/site1.148.sio.pem

# Fusion pour site2.148.sio
cat /etc/haproxy/certs/site2.cert.pem     /etc/haproxy/certs/site2.key.pem     > /etc/haproxy/certs/site2.148.sio.pem

# Sécuriser les fichiers finaux (clé privée dedans)
chmod 600 /etc/haproxy/certs/site1.148.sio.pem
chmod 600 /etc/haproxy/certs/site2.148.sio.pem

# Les fichiers intermédiaires séparés ne sont plus utiles
rm /etc/haproxy/certs/site1.cert.pem /etc/haproxy/certs/site1.key.pem
rm /etc/haproxy/certs/site2.cert.pem /etc/haproxy/certs/site2.key.pem

Vérifier que les fichiers finaux sont bien présents :

ls -lh /etc/haproxy/certs/
# Attendu :
# -rw------- 1 root root  XXXX site1.148.sio.pem
# -rw------- 1 root root  XXXX site2.148.sio.pem

Étape 5 — Démarrer HAProxy

# Vérifier la syntaxe avant de démarrer
haproxy -c -f /etc/haproxy/haproxy.cfg

# Démarrer HAProxy
systemctl start haproxy

Vérifications utiles

Afficher les informations d’un certificat (domaine, dates de validité) :

openssl x509 -in /etc/haproxy/certs/site1.148.sio.pem -noout -text | grep -E "(Subject:|Not Before|Not After)"

Tester que HAProxy répond bien en HTTPS sur la VIP :

# Depuis un poste du réseau interne
# -k ignore l'avertissement du certificat auto-signé
curl -k https://site1.148.sio
curl -k https://site2.148.sio

Vérifier le certificat présenté par HAProxy :

openssl s_client -connect 10.0.0.82:443 -servername site1.148.sio < /dev/null 2>/dev/null | openssl x509 -noout -subject -dates

6. Troubleshooting

6.1 Vérification de la syntaxe HAProxy

À exécuter avant chaque reload ou après toute modification de haproxy.cfg. Retourne les erreurs de configuration sans redémarrer le service.

haproxy -c -f /etc/haproxy/haproxy.cfg
# Attendu : "Configuration file is valid"

6.2 Reload / Restart sans interruption

# Reload gracieux : les connexions actives ne sont pas coupées (préférer cette commande)
systemctl reload haproxy

# Restart complet : coupe toutes les connexions actives (utiliser uniquement si reload impossible)
systemctl restart haproxy

# Vérifier l'état du service
systemctl status haproxy

6.3 Logs en temps réel

# Suivre les logs HAProxy en live (requêtes, erreurs de connexion, health-checks)
journalctl -u haproxy -f

# Filtrer uniquement les erreurs (codes HTTP 5xx ou messages d'erreur HAProxy)
journalctl -u haproxy -f | grep -E "(ERR|5[0-9]{2}|BACKEND|DOWN)"

# Logs Keepalived (bascules VRRP, changements d'état MASTER/BACKUP)
journalctl -u keepalived -f

6.4 Vérification de la VIP et de l’état VRRP

# Vérifier que la VIP est assignée sur le nœud actif (doit apparaître sur le MASTER uniquement)
ip addr show eth0 | grep 10.0.0.82

# Voir les détails de l'instance VRRP (état, priorité, uptime)
systemctl status keepalived

# Depuis un poste externe : vérifier quel nœud détient physiquement la VIP
arping -I eth0 10.0.0.82

6.5 Statistiques et état des backends via socket Unix

# Lister tous les backends et leur état (UP/DOWN) via le socket admin
echo "show servers state" | socat stdio /run/haproxy/admin.sock

# Désactiver manuellement un backend pour maintenance
echo "disable server backend_site1/backend1" | socat stdio /run/haproxy/admin.sock

# Réactiver le backend après maintenance
echo "enable server backend_site1/backend1" | socat stdio /run/haproxy/admin.sock
